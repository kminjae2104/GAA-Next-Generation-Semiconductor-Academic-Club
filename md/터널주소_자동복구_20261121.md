# 터널 주소 소실 자동 복구

2026-11-21 사용자 요청으로 구성하고 실제 주소 교체·결과 왕복을 검증했다.

**2026-11-25 변경:** 사용자가 공개 전환을 요청했다. 아래 비공개 설명은 최초 구성 당시 기록이다. 공개 호환 설정·서명과 인증 유지·중계 교체의 실제 확인 범위는 [협업 설정 기록](협업/설정변경_20261125.md)을 따른다. 원격 계산과 agent는 이 전환 때문에 재시작하지 않는다.

## 고정 접점

기존 비공개 GitHub 저장소의 `gaa-agent-rendezvous` 전용 브랜치에 서명된 endpoint.json만 게시한다. 연구 main 브랜치와 공개 범위는 변경하지 않았다. Windows의 기존 GitHub 인증은 Windows 안에서만 사용하며 Linux에는 이 저장소만 읽는 전용 deploy key를 등록했다. GitHub의 SSH 호스트키는 인증된 공식 API에서 받은 키로 고정 검증한다. [읽기 전용 deploy key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys), [GitHub SSH 443 포트](https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port).

주소 문서는 URL·프로토콜·일련번호·HMAC 서명만 포함한다. 접속 토큰·개인키·서명 비밀키는 Git에 올리지 않는다. 서명 키와 agent 설정은 계정 전용 파일에 저장한다. 변조·잘못된 호스트·과거 일련번호를 거부한다. 원격 Git 버전에 맞춰 GIT_SSH 래퍼와 엄격한 known_hosts 검증을 사용한다.

## 자동 복구 순서

1. Windows `resilient_relay.py`가 터널 프로세스 종료를 감지하거나30초 간격 health가3회 연속 실패하면 새 터널을 만든다.
2. 새 HTTPS 주소를 확인하고 비공개 GitHub 접점에 서명해 게시한다. agent 토큰은 그대로 유지한다. 로컬 relay 프로세스 종료도 재기동한다.
3. Linux agent는 요청 실패 시 최대1분 간격으로 읽기 전용 Git 접점에서 새 문서를 가져와 서명·일련번호·호스트를 검증한다.
4. 새 주소를 개인 설정에 저장하고 같은 요청이나 보관된 결과를 재전송한다. 계산은 다시 제출하지 않는다.
5. Windows 결과 회수 감시도 매 반복 session의 최신 주소를 읽는다. TCAD scheduler는 전 과정과 독립적으로 유지된다.

현재 runtime은 `.local/runtime.json`에 기록한다. 실제 인증 파일은 저장소 밖 `%LOCALAPPDATA%/TCAD_PRIVATE/gaa_resilient_20261120T172247Z/`에 있다. runtime의 route_watchdog.json·discovery_publish.json·route_error.json을 함께 확인하되 과거 오류 시각을 현재 장애로 오해하지 않는다.

## 실제 시험

- 기존 중계를 닫고 별도 주소의 새 중계로 전환했을 때 수동 입력 없이 agent가 재접속했다.
- 새 관리형 임시 터널 프로세스도 실제로 종료했다. 이전 주소 `composer-robert-dom-vegetation.trycloudflare.com`에서 새 주소 `proceedings-beneath-breeding-fighter.trycloudflare.com`으로 자동 교체됐다.
- 원격 discovery_status.json에서 새 URL과 서명 문서 일련번호 갱신을 확인했다. 그 경로로 새 read-only 요청을 보내 결과 ZIP과 해시를 회수했다. 약2분의 자동 복구였으며 입력 장치·클립보드·추가 토큰 입력을 쓰지 않았다.
- 자동화38개 시험 통과. 서명 변조·오키·재전송된 과거 문서·허용되지 않은 호스트 거부를 포함한다.
- [실제 검증 자료](../검증/터널주소_자동복구_20261121.json).

## 가용성 범위

임시 주소 자체의 영구 유지가 아니라, 주소가 바뀌어도 자동으로 다시 찾는 방식이다. Windows PC·원격 서버의 전원과 네트워크, GitHub 접근·Windows 인증 유지가 필요하다. 인터넷이나 GitHub 장애 중에는 기다렸다 재시도한다. Windows 사용자 로그인 전 자동 기동이나 무중단 서비스 SLA는 구성·검증하지 않았다. 서버 재부팅 뒤 agent 기동은 기존 사용자 cron에 의존하며 실제 재부팅 시험은 하지 않았다. 명시적으로 stop.request를 만들면 자동 중지를 존중한다.
