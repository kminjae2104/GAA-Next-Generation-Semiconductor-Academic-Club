# TCAD 도구와 GAA 연구 환경

**학술동아리 부원용 공유 자료 · 2026년 11월 18일**

반도체 시뮬레이션을 처음 접하는 부원을 위한 자료입니다. TCAD 도구의 역할, GAA 계산 과정, 원격 실행과 연구 기록 방법을 소개합니다. 제품 설명은 원 대본의 2026-11-18 조사 내용에 기반하며, 연구 결과는 **같은 날 12:32 KST 회수본**을 기준으로 합니다. 이후 실행 상태를 실시간으로 나타내는 자료는 아닙니다.

## 먼저 알아둘 세 가지

1. **공정 계산·구조 편집·소자 계산은 서로 다른 작업입니다.**
2. **이번 연구의 실제 물리 계산은 Linux 서버의 ATLAS가 수행했습니다.**
3. **그림이나 곡선이 만들어져도 성능 검증이 완료됐다는 뜻은 아닙니다.**

## 1. TCAD는 어떤 문제를 푸는가

TCAD는 *Technology Computer-Aided Design*의 약자로, 반도체 공정과 소자의 특성을 물리 모델로 계산하는 기술입니다. 실제 제작 전에 설계 조건의 영향을 살피고, 측정 결과를 해석하는 데 사용합니다.

| 작업 | 답하려는 질문 | 입력 예시 | 결과 예시 |
| --- | --- | --- | --- |
| 공정 시뮬레이션 | 이 공정으로 어떤 구조가 만들어질까? | 산화·식각·주입·열처리 조건 | 형상·도핑 분포 |
| 구조 편집·메시 준비 | 어떤 구조를 어떤 격자로 계산할까? | 좌표·재료·전극·격자 조건 | 계산용 소자 구조 |
| 소자 시뮬레이션 | 이 구조에 전압을 걸면 어떻게 동작할까? | 구조·물리 모델·전압·온도 | 전류·전위·캐리어 분포 |

**메시(mesh)**는 계산할 영역을 작은 요소로 나눈 격자입니다. 너무 거칠면 중요한 변화를 놓칠 수 있고, 지나치게 촘촘하면 계산 시간과 메모리 사용량이 커집니다. 따라서 메시를 바꿔도 주요 결과가 안정적인지 확인해야 합니다.

출처: [Synopsys TCAD 개요](https://www.synopsys.com/manufacturing/tcad.html), [DevEdit 제조사 매뉴얼 §1.1](https://subversion.xray.aps.anl.gov/trac/AGIPD_TCAD/export/4/references/docs/Silvaco_Manuals/devedit_users1.pdf).

## 2. 프로그램 이름과 역할 한눈에 보기

### Silvaco와 ATHENA는 같은 수준의 이름이 아니다

**Silvaco는 회사 이름이고 ATHENA는 그 회사의 공정 시뮬레이터입니다.** ‘Silvaco를 사용했다’는 표현에는 실제 사용한 제품 이름을 덧붙이는 것이 정확합니다.

```text
Silvaco의 TCAD 도구 — 역할별 분류
│
├─ 공정 계산       ATHENA / Victory Process
├─ 구조·메시 준비  DevEdit / DevEdit 3D / Victory Mesh
├─ 소자 동작 계산  ATLAS / Victory Device
├─ 실행 환경       DeckBuild
└─ 결과 시각화     TonyPlot / TonyPlot3D
```

각 줄을 모두 거쳐야 하는 것은 아닙니다. 구조를 직접 정의할 수도 있고, 공정 계산으로 만든 구조를 소자 계산에 넘길 수도 있습니다.

| 도구 | 주요 역할 | 이번 GAA 작업과의 관계 |
| --- | --- | --- |
| ATHENA | 기존 1D/2D 공정 해석 | 이번 계산에는 사용하지 않음 |
| DevEdit 3D | 3차원 구조 정의·메시 생성 | 사용 |
| ATLAS | 구조에 전압·모델을 적용한 소자 해석 | 5.34.0.R 버전으로 실제 3D 계산 수행 |
| Victory Process | 공정 시뮬레이션 | 비교 설명 대상 |
| Victory Mesh | 메시 준비·처리 | 비교 설명 대상 |
| Victory Device | 소자 동작 해석 | 비교 설명 대상 |
| DeckBuild | 덱 작성·실행 환경 | 배치 실행에 사용 |
| TonyPlot3D | 3차원 결과 표시 | 구조와 저장된 물리량 확인 |

**주의:** ATLAS를 무조건 2D 전용이라고 설명하면 이번 실행과 맞지 않습니다. 또한 구조 편집기로 형상을 만들었다고 해서 실제 공정으로 제작할 수 있다는 것까지 입증되는 것은 아닙니다.

출처: [ATHENA 제조사 매뉴얼](https://ridl.cfd.rit.edu/products/manuals/silvaco/athena_users1.pdf), [DevEdit 매뉴얼](https://subversion.xray.aps.anl.gov/trac/AGIPD_TCAD/export/4/references/docs/Silvaco_Manuals/devedit_users1.pdf), [Victory Process](https://silvaco.com/products/manufacturing/tcad/victory-process/), [Victory Device](https://silvaco.com/products/manufacturing/tcad/victory-device/), [실제 실행 덱](../../연구/01_GAA_IdVg/tcad/gaa_overnight_20261116T080149Z/eq_bicgst_full.in).

### Sentaurus 및 다른 도구와 비교

Sentaurus는 Synopsys의 TCAD 제품군입니다. 제품을 비교할 때는 공정 도구끼리, 구조 편집기끼리, 소자 도구끼리 대응시키면 이해하기 쉽습니다.

| 역할 | Silvaco의 예 | Synopsys의 예 |
| --- | --- | --- |
| 공정 해석 | ATHENA / Victory Process | Sentaurus Process |
| 구조 직접 정의 | DevEdit 3D | Sentaurus Structure Editor |
| 소자 해석 | ATLAS / Victory Device | Sentaurus Device |

위 표는 **역할의 대응 관계**입니다. 문법·모델·정확도·계산 속도가 같다는 뜻은 아닙니다. 우열을 판단하려면 동일한 구조·전압·모델·메시·수렴 기준으로 비교해야 하며, 이번 연구에서는 그러한 도구 간 벤치마크를 수행하지 않았습니다.

다른 선택지로는 공정·소자 도구를 제공하는 **GTS TCAD Framework**, 반도체 방정식과 다른 물리 현상의 연계를 지원하는 **COMSOL Semiconductor Module**이 있습니다. 소자 방정식을 계산하는 기능과 제조 공정 흐름을 모사하는 기능은 구분해서 살펴봐야 합니다.

출처: [Sentaurus Process](https://www.synopsys.com/manufacturing/tcad/process-simulation/sentaurus-process.html), [Sentaurus Structure Editor](https://www.synopsys.com/manufacturing/tcad/structure-editor.html), [Sentaurus Device](https://www.synopsys.com/manufacturing/tcad/device-simulation/sentaurus-device.html), [GTS 공식 자료](https://www.globaltcad.com/wp-content/uploads/2023/07/gts-framework-web.pdf), [COMSOL 공식 설명](https://doc.comsol.com/6.4/doc/com.comsol.help.semicond/semicond_ug_intro.4.04.html).

## 3. 이번 GAA 연구에서 실제로 한 일

**GAA(Gate-All-Around)**는 게이트가 채널 단면의 둘레를 감싸는 구조입니다. 이번 대상은 단일 사각 실리콘 나노와이어이며, 여러 장의 넓은 nanosheet를 적층한 구조와는 다릅니다.

| 항목 | 기준 설계 |
| --- | --- |
| 게이트 길이 | 40 nm |
| 실리콘 단면 | 10 × 10 nm |
| SiO₂ 두께 | 1 nm |
| 온도 | 300 K |
| 전류 방향 | z축 |
| 평가 Vds | 0.05 V / 0.6 V |
| 목표 게이트 스윕 | Vgs = −0.2~0.8 V |
| 전류 정규화 기준 | 단일 wire 둘레 40 nm = 0.04 µm |

이번 단계에서는 **DevEdit 3D로 최종 구조를 직접 정의하고 ATLAS로 동작을 계산**했습니다. 성장·식각·열처리를 순서대로 재현한 제조 공정 시뮬레이션은 수행하지 않았습니다.

```text
치수·재료·영역 설정
        ↓
DevEdit 3D : 구조·메시 생성
        ↓  geometry.str
ATLAS : 도핑·물리 모델·전압 설정 → 수치 계산
        ├─ .str : 구조와 저장된 상태 → TonyPlot3D로 확인
        └─ .log / .dat : 전압·단자 전류 → Python으로 검증·분석
```

| 파일·용어 | 읽는 방법 |
| --- | --- |
| 덱(deck), `.in` | 시뮬레이터에 수행할 작업을 지시하는 입력 파일 |
| `geometry.str` | 구조 생성 단계의 저장 파일. 이번 흐름에서는 도핑을 ATLAS에서 추가 |
| `final_high.str` | high 바이어스 계산 뒤 저장한 상태. 파일 이름만으로 목표 전압 도달을 보장하지 않음 |
| `.log` | 시뮬레이터가 기록한 실제 전압·단자 전류 |
| `.dat` | 로그 등에서 추출한 수치 데이터 |

설계와 결과의 출처: [사전 목표](../../연구/01_GAA_IdVg/md/설계와목표.md), [실제 덱](../../연구/01_GAA_IdVg/tcad/gaa_overnight_20261116T080149Z/eq_bicgst_full.in), [회수 결과 검증](../../검증/GAA_발표_20261118_최신회수/검증기록.json).

## 4. 원격 연구 환경은 어떻게 연결되는가

### 사람이 접속하는 경로

```text
개인 PC
   ↓ 원격 데스크톱
실습실 Windows PC
   ↓ MobaXterm으로 SSH 접속
학내 Linux 계산 서버
   └─ Silvaco 실행
```

실습실 PC는 접속 창구이고, **실제 소자 계산은 Linux 서버**가 수행합니다. MobaXterm은 명령·파일·프로그램 화면을 주고받는 도구입니다.

### 등록 후 자동화가 동작하는 경로

```text
개인 PC : VS Code·Codex·Python
   ↓ 작업 패키지 준비
인증된 HTTPS 파일 중계
   ⇅ 작업·상태·결과 전송
Linux agent
   ↓ 독립 세션의 Python 스케줄러
DeckBuild → DevEdit 3D → ATLAS
   └─ 결과 파일을 중계를 통해 개인 PC로 회수
```

**agent**는 서버에서 작업을 받아 실행·전송하는 프로그램이고, **스케줄러**는 작업의 순서와 동시 실행 수를 관리하는 프로그램입니다. 최초 등록 후에는 반복 실행과 회수에 원격 화면 입력이 필요하지 않도록 구성했습니다.

독립 세션에 제출한 계산은 원격 데스크톱 창과 분리됩니다. 다만 서버 전원·라이선스·프로그램 오류에 따라 중단될 수 있습니다. 파일 통신에는 중계 PC의 전원·네트워크·프로그램과 유효한 인증이 필요하며, 연결이 끊기면 회수가 지연될 수 있습니다.

| 도구 | 이 연구에서 맡은 일 |
| --- | --- |
| VS Code | 덱·코드·문서 편집 |
| Codex | 덱·자동화 코드·분석 작성 보조 |
| Python | 작업 제출·회수·로그 판독·수치 검증 |
| ATLAS | 물리 방정식을 풀어 실제 시뮬레이션 결과 생성 |

AI가 작성한 설명이나 숫자를 실제 시뮬레이션 결과로 취급하지 않습니다. 자동화 시험 통과와 소자 물리 검증도 별개의 판정입니다.

출처: [자동화 구성 기록](../백그라운드자동화.md), [독립 실행 기록](../무인야간운용.md), [실제 회수 기록](../../검증/GAA_발표_20261118_최신회수/presentation_snapshot.json). 특정 접속 주소·계정·인증값 없이 역할만 설명했습니다.

## 5. Git과 GitHub로 연구를 기록하는 방법

**Git은 파일의 변경 이력을 기록하는 도구이고, GitHub는 Git 저장소를 온라인에서 보관·협업하는 서비스입니다.**

```text
파일 수정 → commit : 로컬에 변경 이력 기록
                 ↓ push
           GitHub 원격 저장소
                 ↓ clone / pull
           다른 환경에서 코드·문서 받기
```

| 용어 | 의미 |
| --- | --- |
| 저장소(repository) | 프로젝트 파일과 Git 이력을 관리하는 단위 |
| commit | 선택한 변경 내용을 로컬 이력에 기록 |
| push | 로컬 commit을 원격 저장소로 전송 |
| clone | 원격 저장소를 처음 내려받음 |
| pull | 원격 변경 내용을 가져와 현재 브랜치에 반영 |

GitHub 자체가 소자의 전류를 계산하는 것은 아닙니다. 이번 환경에서는 Linux 서버가 계산하고 Git·GitHub는 입력·분석 코드·문서의 이력을 관리합니다.

연구를 다시 확인하려면 코드 외에도 **실행 ID, 입력 조건, 시뮬레이터 버전, 모델, 실제 로그**가 필요합니다. 원시 결과는 실행 ID별로 보존하고, **해시(hash)**라는 파일 식별값으로 내용이 바뀌었는지 대조합니다. 비밀번호·토큰·라이선스 파일은 저장소에 넣지 않습니다.

출처: [GitHub 공식 설명](https://docs.github.com/en/get-started/start-your-journey/what-is-github), [연구 저장소 규칙](../../AGENTS.md).

## 6. 결과의 성공 여부는 어떻게 판단하는가

```text
실행 제출 → 실행 확인 → 정상 종료·필수 출력 확인
    → 실제 바이어스·스윕 범위 확인 → 전류 보존·지표 검사
    → 메시 비교 → 물리 모델 보정·외부 자료와 비교
```

### 성능 지표 읽기

| 지표 | 뜻 | 이번 기준 |
| --- | --- | --- |
| Ion | 켰을 때의 드레인 전류 | Vgs=Vds=0.6 V |
| Ioff | 껐을 때도 흐르는 드레인 전류 | Vgs=0 V, Vds=0.6 V |
| Ion/Ioff | 켜짐과 꺼짐의 전류비 | ≥10⁶ 목표 |
| Vth | 소자가 켜지는 기준 전압 | 일정전류법으로 추출 |
| SS | 전류를 10배 바꾸는 데 필요한 게이트 전압 | 고정 전류창에서 추출 |
| DIBL | 드레인 전압에 따른 Vth 변화 | 두 Vds 결과로 계산 |
| KCL 검사 | 단자 전류의 합이 허용 오차 안에서 0인지 확인 | 각 계산점에서 검사 |

전류의 **A/wire**와 **A/µm**는 다릅니다. 이 단일 wire의 경우 `I[A/µm] = I[A] ÷ 0.04 µm`입니다. 서로 다른 정규화 기준의 숫자를 그대로 비교하면 안 됩니다.

### 이번 결과에서 배운 사례

아래는 2026-11-18 12:32 KST 회수본에 대한 판정입니다.

| 결과 | 확인된 내용 | 판정 |
| --- | --- | --- |
| 기준 4.5 eV fine | 전체 목표 스윕과 full–fine 메시 비교 확보 | 수치 검증 통과. 누설·전류비 목표는 미달 |
| 일함수 4.6 eV fine | 실제 Vds≈0.3407 V | 목표 0.6 V 조건의 성능으로 채택 불가 |
| BQP fine | Vgs≈0.58484 V에서 종료 | 목표 0.8 V까지 미완료 |

기준 소자의 Ion은 **599.739 µA/µm**로 목표 100 이상을 만족했지만, Ioff는 **1.70061 nA/µm**로 목표 1 이하를 넘었고, Ion/Ioff는 **약 3.53×10⁵**로 목표 10⁶에 미달했습니다. 양자·계면·누설 등 물리 모델의 보정도 남아 있습니다.

따라서 현재 성과는 **“기준 GAA의 전기적 동작과 메시 안정성을 확인했다”**입니다. **“실용 소자의 모든 성능 검증을 완료했다”**는 결론은 아닙니다. 후속 연구에서는 수렴 문제를 분석하고 분기별 메시·물리 모델 검증을 진행합니다.

## 자주 나오는 질문

**Q. 왜 공정 시뮬레이션부터 하지 않았나요?**\
이번 단계는 직접 정의한 기준 구조의 동작을 먼저 확인하는 목적입니다. 실제 제조 가능성은 별도로 검증해야 합니다.

**Q. 더 새로운 프로그램이면 더 정확한가요?**\
그렇게 단정할 수 없습니다. 필요한 물리 모델·보정·격자와 실제 조건의 일치 여부가 중요합니다. 이번에 도구 간 동일 조건 벤치마크는 하지 않았습니다.

**Q. 원격 창을 닫으면 계산도 끝나나요?**\
이번에는 서버의 독립 세션으로 제출해 창과 분리했습니다. 다만 서버·프로세스 장애까지 막는 것은 아닙니다.

**Q. 구조 사진이나 매끄러운 그래프가 있으면 성공인가요?**\
구조 표시, 정상 종료, 목표 전압 도달, 수치 검증, 물리 검증을 각각 확인해야 합니다.
