# TCAD 도구와 나의 GAA 연구 환경 — 발표 대본

작성일: 2026-11-18. 대상: TCAD·원격 실행·Git을 처음 접하는 학부생. 약 12~15분을 가정한 대본이며 실제 시간은 낭독 속도에 따라 조절한다. 인용 링크와 ‘발표 메모’는 읽지 않는다. 모식도는 이미지 생성 없이 텍스트로 작성했다.

## 1. 도입 — 컴퓨터 안에서 소자를 만든다는 뜻

### 화면에 보여줄 문장

> 구조를 만들고 → 물리 방정식을 계산하고 → 결과를 검증한다

### 발표 대본

안녕하세요. 오늘은 제가 GAA 소자를 연구하면서 어떤 프로그램을 사용했고, 제 PC와 실습실 컴퓨터를 어떻게 연결해 계산했는지 설명드리겠습니다.

먼저 TCAD는 반도체를 실제로 만들기 전에 공정이나 소자의 동작을 컴퓨터로 계산하는 도구입니다. 예를 들어 산화막을 형성하면 구조가 어떻게 바뀌는지, 완성된 트랜지스터에 전압을 걸면 전류가 얼마나 흐르는지 살펴봅니다.

여기서 구조를 만드는 일과 전류를 계산하는 일은 구분해야 합니다. 오늘 나오는 프로그램 이름도 이 역할에 따라 나누면 이해하기 쉽습니다. 공정 시뮬레이터는 어떻게 만들지를 계산하고, 구조 편집기는 어떤 모양을 계산할지 정의하며, 소자 시뮬레이터는 그 구조가 어떻게 동작할지를 계산합니다.

근거: [Synopsys TCAD 개요](https://www.synopsys.com/manufacturing/tcad.html), [Silvaco TCAD 개요](https://silvaco.com/products/manufacturing/tcad/).

## 2. Silvaco와 ATHENA — 회사와 제품의 관계

### 화면용 모식도 ①

```text
Silvaco : 회사 / TCAD 제품군
│
├─ 공정 계산       ATHENA / Victory Process
├─ 구조·메시 준비  DevEdit / DevEdit 3D / Victory Mesh
├─ 소자 동작 계산  ATLAS / Victory Device
├─ 실행 환경       DeckBuild
└─ 결과 시각화     TonyPlot / TonyPlot3D
```

발표 메모: 이 도식은 역할 분류다. 각 줄을 모두 거쳐야 하는 단일 실행 순서나 모든 제품의 완전한 목록을 뜻하지 않는다.

### 발표 대본

먼저 Silvaco와 ATHENA의 관계부터 정리하겠습니다. Silvaco는 회사 이름이고, ATHENA는 Silvaco가 제공하는 공정 시뮬레이터의 이름입니다. 따라서 Silvaco와 ATHENA를 경쟁 프로그램처럼 비교하면 회사 이름과 제품 이름이 섞이게 됩니다.

‘Silvaco를 사용했다’는 말만으로는 구체적으로 무엇을 했는지 알기 어렵습니다. 공정 계산에 ATHENA를 사용했는지, 전기적 특성 계산에 ATLAS를 사용했는지까지 말해야 작업이 명확해집니다.

제 연구는 Silvaco 도구 중 DevEdit 3D와 ATLAS를 사용한 작업입니다. ATHENA와 Victory의 공정 흐름을 소개하지만, 이번 GAA 결과를 그 프로그램으로 계산한 것으로 표현하지는 않겠습니다.

근거: [ATHENA 제조사 매뉴얼](https://ridl.cfd.rit.edu/products/manuals/silvaco/athena_users1.pdf), [Silvaco 제품군](https://silvaco.com/products/manufacturing/tcad/), [실제 GAA 덱](../../연구/01_GAA_IdVg/tcad/gaa_overnight_20261116T080149Z/eq_bicgst_full.in).

## 3. ATHENA와 DevEdit 3D — 공정을 따라갈 것인가, 구조를 직접 만들 것인가

### 화면용 비교표

| 구분 | ATHENA | DevEdit 3D |
| --- | --- | --- |
| 주된 역할 | 공정 시뮬레이션 | 구조 생성·편집 및 메시 준비 |
| 입력의 관점 | 산화·주입·확산 등 공정 조건 | 영역·좌표·재료·메시 조건 |
| 알고 싶은 것 | 공정으로 생기는 형상·도핑 분포 | 원하는 계산 구조와 격자 |
| 이번 연구 사용 | 사용하지 않음 | 사용함 |

### 발표 대본

ATHENA에서는 실제 제작 과정을 따라가며 구조와 도핑 분포를 계산합니다. 예를 들어 이온을 주입하고 열처리하면 불순물이 어디까지 퍼지는지 살펴볼 수 있습니다. 기본적으로 1차원과 2차원 공정 해석을 설명하는 기존 도구입니다.

반면 DevEdit는 소자 구조를 직접 만들거나 수정하고, 계산에 필요한 메시를 준비하는 도구입니다. DevEdit 3D에서는 영역의 입체적인 범위를 정의해 3차원 구조를 만들 수 있습니다.

건축에 비유하면 공정 시뮬레이션은 공사 과정을 따라가며 결과를 예측하는 일이고, 구조 편집은 분석할 건물의 모양을 직접 정의하는 일에 가깝습니다. 다만 구조를 직접 만들었다고 해서 그 구조를 실제 공정으로 만들 수 있음까지 증명되는 것은 아닙니다.

근거: [ATHENA 매뉴얼의 1D/2D 설명](https://ridl.cfd.rit.edu/products/manuals/silvaco/athena_users1.pdf), [DevEdit 제조사 매뉴얼 §1.1](https://subversion.xray.aps.anl.gov/trac/AGIPD_TCAD/export/4/references/docs/Silvaco_Manuals/devedit_users1.pdf).

## 4. ATLAS와 Victory — 이름보다 역할을 구분하기

### 화면용 비교표

| 역할 | 기존 도구 계열 | 현재 소개되는 Victory 계열 |
| --- | --- | --- |
| 공정 해석 | ATHENA | Victory Process |
| 메시 준비 | DevEdit 등 | Victory Mesh |
| 소자 해석 | ATLAS | Victory Device |

### 발표 대본

ATLAS는 준비된 소자 구조에 전압과 물리 모델을 적용해 전류와 내부 상태를 계산하는 도구입니다. 제 연구에서는 ATLAS 5.34.0.R로 실제 3차원 소자를 계산했습니다. 따라서 ATLAS를 무조건 2차원 전용 프로그램이라고 설명하면 이번 실행과 맞지 않습니다.

Victory도 하나의 단일 역할 이름으로 이해하면 혼동하기 쉽습니다. Victory Process는 공정을, Victory Mesh는 메시를, Victory Device는 소자 동작을 맡습니다. 현재 제조사 안내는 이 Victory 흐름을 중심으로 설명합니다.

제 연구에서 기존 ATLAS를 사용한 것은 확보된 환경에서 실행과 결과를 검증했기 때문입니다. 도구를 바꾸면 입력 호환성뿐 아니라 물리 모델과 결과도 다시 확인해야 합니다. 이름이 더 새롭다는 이유만으로 제 소자의 계산 정확도가 자동으로 높아지는 것은 아닙니다.

근거: [Victory Process](https://silvaco.com/products/manufacturing/tcad/victory-process/), [Victory Device 및 ATLAS 호환성 안내](https://silvaco.com/products/manufacturing/tcad/victory-device/), [실제 ATLAS 실행 기록](../../검증/GAA_발표_20261118_최신회수/原始資料/eq_bicgst_fine/process.json). 제품 현황은 2026-11-18 웹 확인 기준이다.

## 5. Sentaurus와 비교 — 같은 역할끼리 대응시키기

### 화면용 비교표

| 역할 | Silvaco의 예 | Synopsys Sentaurus의 예 |
| --- | --- | --- |
| 공정 해석 | ATHENA / Victory Process | Sentaurus Process |
| 구조 직접 정의 | DevEdit 3D | Sentaurus Structure Editor |
| 소자 동작 해석 | ATLAS / Victory Device | Sentaurus Device |

### 발표 대본

다른 대표적인 TCAD 제품군으로는 Synopsys의 Sentaurus가 있습니다. 여기서도 회사와 제품군, 개별 도구의 이름을 구분하면 됩니다.

Sentaurus Process는 공정 시뮬레이터이고, Sentaurus Device는 완성된 소자의 동작을 계산하는 도구입니다. 구조를 직접 정의하는 Sentaurus Structure Editor도 있습니다. 따라서 ATHENA와 Sentaurus Device를 바로 비교하기보다는 공정 도구끼리, 소자 도구끼리 비교하는 것이 적절합니다.

이 표는 기능의 대략적인 대응 관계입니다. 문법과 모델이 같다는 뜻은 아닙니다. 두 도구의 정확도나 속도를 비교하려면 같은 구조, 재료, 전압, 물리 모델, 메시와 수렴 조건을 맞춰야 합니다. 저는 이번 연구에서 Sentaurus와 동일 조건의 성능 비교를 실행하지 않았으므로 어느 쪽이 더 정확하다고 결론 내리지 않겠습니다.

근거: [Sentaurus Process](https://www.synopsys.com/manufacturing/tcad/process-simulation/sentaurus-process.html), [Sentaurus Device](https://www.synopsys.com/manufacturing/tcad/device-simulation/sentaurus-device.html), [Sentaurus Structure Editor](https://www.synopsys.com/manufacturing/tcad/structure-editor.html). 비교 조건에 관한 설명은 본 발표의 연구 방법상 판단이다.

## 6. 다른 반도체 해석 프로그램

### 화면용 비교표

| 제품군 | 확인한 기능 | 비교할 때의 관점 |
| --- | --- | --- |
| Silvaco TCAD | 공정·구조·소자 해석 | 이번 연구의 실행 환경 |
| Synopsys Sentaurus | 공정·구조·소자 해석 | 동일 역할의 도구끼리 비교 |
| GTS TCAD Framework | ProEmu 공정, Minimos-NT 소자 해석 등 | 지원 모델·소자·작업 흐름 확인 |
| COMSOL Semiconductor Module | 반도체 방정식 및 다른 물리와의 연계 | 공정 전용 도구와 역할 차이 확인 |

### 발표 대본

선택지는 Silvaco와 Sentaurus만 있는 것은 아닙니다. GTS도 공정과 소자 시뮬레이션 도구를 제공하고, COMSOL의 Semiconductor Module도 반도체 소자의 전하와 전류를 계산합니다.

특히 COMSOL은 여러 물리 현상을 연결하는 환경을 제공합니다. 다만 반도체 소자 방정식을 풀 수 있다는 것과 산화, 식각, 주입으로 이어지는 공정 흐름을 전용 도구처럼 제공한다는 것은 다른 이야기입니다.

그래서 프로그램을 선택할 때는 유명한 이름 하나를 고르기보다 내가 풀 문제가 공정인지, 전기적 동작인지, 열이나 광학과 결합된 문제인지부터 정해야 합니다. 그다음 필요한 모델과 라이선스, 계산 자원, 예제와 검증 자료를 확인해야 합니다.

근거: [GTS 공식 Framework 자료](https://www.globaltcad.com/wp-content/uploads/2023/07/gts-framework-web.pdf), [COMSOL Semiconductor Module 공식 설명](https://doc.comsol.com/6.4/doc/com.comsol.help.semicond/semicond_ug_intro.4.04.html). 가격·우열·시장점유율은 조사하지 않았다.

## 7. 이번 연구에서 실제로 계산한 것

### 화면용 모식도 ②

```text
치수·재료·영역 설정
        │
        ▼
DevEdit 3D ── 구조·메시 생성 ── geometry.str
                                      │
                                      ▼
                         ATLAS: 도핑·모델·전압 설정
                                      │
                          물리 방정식의 수치 계산
                                      │
                    ┌─────────────────┴────────────────┐
                    ▼                                  ▼
              .str 저장 상태                     .log / .dat
          형상·저장된 물리량                    전압·단자 전류
                    │                                  │
                    ▼                                  ▼
              TonyPlot3D                       Python 검증·지표 추출
```

### 발표 대본

이제 도구 이름을 제 연구에 연결해 보겠습니다. 저는 길이 40나노미터의 게이트와 10 곱하기 10나노미터의 실리콘 단면을 갖는 단일 사각 GAA 구조를 정의했습니다. 전류가 흐르는 방향은 z축입니다.

DevEdit 3D에서 영역과 메시를 만든 뒤 ATLAS에서 도핑과 물리 모델을 설정하고 전압을 변화시켰습니다. 여기서는 실제 GAA 제조 공정 전체를 재현한 것이 아니라, 직접 정의한 구조의 동작을 평가했습니다.

결과 파일의 역할도 다릅니다. str 파일은 구조와 저장된 상태를 확인하는 데 사용합니다. log와 dat 파일은 전압과 단자 전류를 확인하고 성능 지표를 계산하는 데 사용합니다. 따라서 3차원 그림이 보기 좋게 나왔다고 해서 원하는 전압에서 정상 동작한 것까지 확인한 것은 아닙니다.

## 8. 내 PC, 실습실 PC, Linux 서버의 역할

### 화면용 모식도 ③ — 사람의 접속 경로

```text
[내 PC]
   │ 원격 데스크톱 접속
   ▼
[실습실 Windows PC]
   │ MobaXterm: SSH 터미널 / 파일 전송 / X11 화면 표시
   ▼
[학내 Linux 서버: semicon1, cau103 계정]
   └─ Silvaco 실행과 실제 수치 계산
```

### 화면용 모식도 ④ — 등록 이후의 자동 실행·회수 경로

```text
[내 PC: VS Code·Codex·Python]
   │ 덱·검증 명령·파일을 작업 패키지로 준비
   ▼
[인증된 임시 HTTPS 파일 중계]
   ⇅ 작업·상태·결과 파일 교환
[Linux agent]
   │ 독립 세션의 Python 스케줄러
   ▼
[DeckBuild → DevEdit 3D → ATLAS]
   │ 로그·구조·검증 기록
   └────────── 중계를 통해 내 PC로 회수
```

### 발표 대본

제 작업 환경에서 가장 헷갈리기 쉬운 부분은 컴퓨터가 여러 대라는 점입니다. 제가 조작하는 내 PC, 실습실의 Windows PC, 그리고 Silvaco가 계산하는 Linux 서버를 나눠 생각하면 됩니다.

실습실 PC에서는 MobaXterm으로 Linux에 접속합니다. MobaXterm은 전류를 계산하는 프로그램이 아니라 서버에 명령을 전달하고 파일과 화면을 주고받는 접속 도구입니다. 실제 소자 계산은 Linux 서버에서 실행됩니다.

자동화에서는 이 경로에 파일 중계와 agent를 추가했습니다. 최초 등록 뒤에는 agent가 작업 파일을 받아 실행하고 결과를 돌려줍니다. 따라서 매번 원격 창에 직접 명령을 타이핑할 필요가 줄었습니다.

계산은 서버의 독립 세션에서 실행되도록 구성했습니다. 그래서 원격 창이 닫히는 것과 계산이 종료되는 것을 분리했습니다. 다만 서버 전원, 라이선스, 프로그램 오류까지 해결되는 것은 아니고, 중계가 끊기면 결과 회수도 늦어질 수 있습니다.

근거: [기존 접속 구조와 자동화 기록](../백그라운드자동화.md), [독립 실행 운용 기록](../무인야간운용.md), [이번 세션의 실제 회수 기록](../../검증/GAA_발표_20261118_최신회수/presentation_snapshot.json). 도식은 연구에 사용한 경로이며 현재 모든 연결의 상시 가용성을 보증하지 않는다.

## 9. VS Code, Codex, Python은 각각 무엇을 했는가

### 화면용 비교표

| 도구 | 쉬운 설명 | 이번 작업에서의 역할 |
| --- | --- | --- |
| VS Code | 코드·문서를 작성하는 작업 공간 | 덱·Python·마크다운 편집 |
| Codex | 코드와 문서 작성을 돕는 AI 작업 도구 | 덱·자동화 코드·분석 작성 보조 |
| Python | 반복할 절차를 프로그램으로 적는 언어 | 제출·회수·로그 판독·수치 검증 |
| ATLAS | 소자 물리 계산 프로그램 | 방정식을 풀어 전류·상태 계산 |

### 발표 대본

내 PC에서는 VS Code로 파일을 편집하고 Codex의 도움을 받아 덱과 자동화 코드를 작성했습니다. 여기서 물리 계산 결과의 출처는 ATLAS입니다. AI가 제시한 숫자를 시뮬레이션 결과로 사용한 것은 아닙니다.

Python은 정해진 반복 작업을 처리합니다. 작업이 끝났는지 확인하고, 결과 파일을 회수하고, 로그에서 필요한 수치를 읽고, 후속 작업의 선행 조건을 검사합니다. 미리 정의하지 않은 물리 모델을 Python이 스스로 연구해 선택하는 구조는 아닙니다.

계속 바뀌지 않는 감시 작업은 Python이 맡도록 해서 AI 모델을 반복 호출하는 비용도 줄였습니다. 다만 자동화된 검사가 통과했다는 것과 소자의 물리가 현실에 맞는다는 것은 구분했습니다.

## 10. Git과 GitHub — 연구 기록을 남기는 방법

### 화면용 모식도 ⑤

```text
파일 수정 ── Git commit ── 로컬 변경 이력
                              │ push
                              ▼
                       GitHub 원격 저장소
                              │ clone / pull
                              ▼
                      다른 환경에서 작업 복원

원시 결과: 실행 ID별 폴더 보존 + 입력·출력 해시 기록
대용량 구조·비밀값: 일반 코드 저장소와 구분해 관리
```

### 발표 대본

Git은 파일의 변경 이력을 남기는 버전 관리 도구이고, GitHub는 Git 저장소를 온라인에서 보관하고 협업하는 서비스입니다. 둘은 같은 이름의 프로그램이 아닙니다.

예를 들어 산화막 두께를 바꾸거나 전압 간격을 수정했을 때, 무엇을 왜 바꿨는지 기록하면 이전 조건으로 돌아가거나 두 조건을 비교하기 쉬워집니다. commit은 로컬에 변경 기록을 남기는 것이고, push는 그 기록을 GitHub 쪽으로 보내는 것입니다. 로컬에서 저장했다고 자동으로 GitHub에 올라간 것은 아닙니다.

다만 GitHub 자체가 제 소자의 전류를 계산하는 것은 아닙니다. 계산은 서버에서 하고, 저장소는 입력과 분석 코드, 문서의 이력을 관리합니다. 원시 결과는 실행 ID로 구분하고, 큰 구조 파일과 비밀번호·토큰은 별도로 관리합니다.

Git 기록은 재현성을 돕지만, 사용한 버전과 물리 모델, 입력 파일, 실제 로그가 함께 있어야 계산을 제대로 추적할 수 있습니다.

근거: [GitHub 공식 Git·GitHub 설명](https://docs.github.com/en/get-started/start-your-journey/what-is-github), [저장소 규칙](../../AGENTS.md). 이 도식은 일반 작업 흐름이며 이번 대본 파일을 commit·push했다는 의미는 아니다.

## 11. 결과를 믿기 위해 확인한 것

### 화면용 모식도 ⑥

```text
실행 제출
   → 실제 실행 확인
   → 종료 코드·필수 출력 확인
   → 실제 전압·전체 스윕 범위 확인
   → 전류 보존·지표 추출 확인
   → 메시 변화에 대한 안정성 확인
   → 물리 모델 보정·외부 근거와 비교
```

### 발표 대본

이번 작업에서 배운 중요한 점은 실행이 끝났다는 표시만으로 결과를 채택할 수 없다는 것입니다.

실제로 어떤 fine 계산에서는 ATLAS가 종료되고 파일도 만들어졌지만, 실제 드레인 전압이 목표 0.6볼트에 도달하지 않았습니다. 또 BQP fine에서는 드레인 전압은 맞았지만 게이트 스윕이 목표까지 가지 못했습니다. 이런 결과를 정상 성능 표에 섞으면 비교 조건이 달라집니다.

그래서 저는 실제 로그의 전압, 전체 스윕, 전류 보존, 메시 비교를 나눠 확인했습니다. 기준 소자의 메시 비교는 통과했지만 누설과 전류비 목표는 미달했습니다. 일함수 변경의 full 결과는 목표에 들어왔으나 fine 검증과 물리 모델 보정이 남아 있습니다.

이 결과의 기준 시각은 11월 18일 12시 32분 회수본입니다. 발표 시점의 실행 현황은 바뀔 수 있으므로, 이 숫자를 실시간 상태라고 소개하지 않겠습니다.

## 12. 마무리 — 이번 연구에서 도구를 연결한 방식

### 발표 대본

오늘 설명한 도구들을 한 문장으로 정리하면, 구조를 정의하는 도구와 물리를 계산하는 도구를 연결하고, 그 실행과 기록을 자동화한 것입니다.

제 연구에서는 DevEdit 3D로 구조와 메시를 만들고 ATLAS로 소자 동작을 계산했습니다. 내 PC에서는 코드와 문서를 관리하고, Linux 서버에서는 실제 계산을 수행했습니다. Git과 GitHub는 변경 이력을 관리하는 역할을 맡았습니다.

앞으로는 실패한 수치 조건을 분석하고 각 분기의 메시 검증을 마친 뒤, 물리 모델을 보정하며 치수 변화 연구로 확장하려고 합니다. 자동화의 목적도 실행 횟수를 늘리는 데서 그치지 않고, 어떤 조건에서 어떤 결과가 나왔는지 다시 확인할 수 있게 만드는 데 있습니다. 감사합니다.

## 발표 준비 메모

- 7분 정도로 줄일 때: 2~5의 제품 비교를 한 표로 묶고 6의 타 도구 소개는 30초로 줄인다. 7~11의 실제 연구 환경·검증은 유지한다.
- 첫 등장 시 이름을 화면에 함께 표기한다: 실바코(Silvaco), 아테나(ATHENA), 데브에디트 3D(DevEdit 3D), 아틀라스(ATLAS), 빅토리(Victory), 센타우러스(Sentaurus).
- ‘실바코가 계산했다’보다 ‘실바코의 ATLAS로 계산했다’라고 말한다.
- ‘원격 PC가 계산했다’보다 실제 Linux 계산 서버와 접속용 Windows PC를 구분해 말한다.
- 도구별 실제 성능 벤치마크는 수행하지 않았다. ‘A가 더 정확하다’, ‘B가 더 빠르다’는 문장은 넣지 않는다.
- 모식도는 구조·역할·흐름을 설명하는 개념도이며 실제 GAA 소자의 3D 구조 사진이 아니다.

## 예상 질문과 짧은 답변

**Q. 왜 ATHENA로 GAA를 만들지 않았나요?**
A. 이번 단계는 최종 구조의 전기적 동작을 먼저 확인하는 목적이어서 DevEdit 3D로 직접 정의했습니다. 제조 공정 전체의 타당성은 아직 검증하지 않았습니다.

**Q. Codex가 전류를 계산하나요?**
A. 코드·분석 작성을 보조했고, 소자 물리 계산은 ATLAS가 수행했습니다. 결과는 실제 로그로 확인했습니다.

**Q. VS Code나 GitHub를 닫으면 계산도 멈추나요?**
A. 이미 서버의 독립 세션에 제출한 계산은 이 프로그램들의 창과 분리했습니다. 다만 서버·라이선스·프로세스 오류 등으로 중단될 수 있고, 연결이 끊기면 결과 회수가 지연될 수 있습니다.

**Q. 그림이 나오면 성공한 것 아닌가요?**
A. 구조 표시, 정상 실행, 목표 전압 도달, 수치 검증, 물리 검증을 각각 확인해야 합니다.

**Q. 이 파일은 GitHub에도 올라갔나요?**
A. 대본 작성과 원격 저장소 업로드는 별개입니다. 이번 작업은 로컬 마크다운 작성이며 commit·push는 수행하지 않았습니다.
