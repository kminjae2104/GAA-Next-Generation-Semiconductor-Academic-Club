# TCAD 실험 공유 규칙

## 작업 단위와 저장 경로

한 실행은 `연구/팀원실험/이름/주제/실행ID/` 한 폴더로 보존한다. 이름은 [팀원명단](팀원명단.md)의 표기를 사용하고, 주제와 실행 ID는 영문·숫자·`_`·`-`로 짓는다. 실행 ID 예: `20261125_lg40_r01`. 실패 뒤 덱을 수정하면 `r02` 등 새 ID를 사용한다. 실행 날짜가 다르면 날짜도 바꾼다.

```text
연구/팀원실험/권도현/gate_length/20261125_lg40_r01/
  README.md                 실행 한눈에 보기
  md/
    사전계획.md              결과를 보기 전에 고정한 목표·조건
    실행정보.md              실제 버전·명령·종료·시각
    결과요약.md              관찰·해석·한계·다음 실험
  tcad/                     이 실행에 실제 사용한 덱/사양
  python/                   분석·그림 생성 코드
  검증/
    raw/                    원시 로그·export·종료 기록
    검증기록.md              수치/물리 검증을 구분
    원본목록.md              원본 위치·크기·SHA-256
  그림/                     원시 근거와 연결된 그림
```

`python/collaboration/new_run.py`는 위 구조와 문서만 만든다. TCAD를 실행하거나 측정값을 만들지 않는다. `check_workspace.py`는 필수 경로·링크·과대 파일·위험 파일명 등을 검사한다. 통과해도 내용의 진실성이나 물리 검증은 보장하지 않는다.

기존 `연구/01_GAA_IdVg/`, `검증/`의 과거 실행과 자동화 경로는 유지한다. 새 팀 실험 때문에 기존 덱이나 로그를 옮기거나 덮어쓰지 않는다. 공통 기준 수정은 별도 PR로 제안한다.

## 사전계획에 적을 것

- 목적·가설, 비교 기준의 경로/커밋/실행 ID, 이번에 바꿀 변수와 고정할 변수.
- 구조 치수·재료·도핑·전극·온도·Vgs/Vds 범위와 간격·메시·물리 모델·보정 상태.
- 추출 정의: 단일 소자 A인지 둘레 정규화 A/um인지, 둘레와 식, Ion/Ioff/SS/Vth/DIBL의 바이어스·전류창.
- 합격 기준과 실패/추출불가 처리. 결과를 본 뒤 기준을 낮추지 않는다.
- 원시 결과 보관 위치와 실행 환경. 개인 암호나 서버 접속 비밀은 기록하지 않는다.

기존 기준 소자의 목표는 [설계와목표](../../연구/01_GAA_IdVg/md/설계와목표.md)에 있다. 다른 소자·모델·바이어스로 바꿀 때 기존 수치와 직접 같은 결과라고 비교하지 않는다.

## 상태를 나누어 보고하기

| 구분 | 가능한 기록 |
| --- | --- |
| 계산 | NOT_RUN / QUEUED / RUNNING / COMPLETED / FAILED |
| 출력 수치 검사 | NOT_VALIDATED / PASS / FAIL / NOT_EXTRACTABLE |
| 메시 수렴 | NOT_VALIDATED / PASS / FAIL |
| 모델 보정·물리 타당성 | NOT_VALIDATED / 범위와 근거를 명시한 판정 |

`COMPLETED`는 종료 코드와 실제 정상 종료 로그 등 근거를 확인했을 때 쓴다. `PASS`는 **어떤 검사**가 통과했는지 적는다. 정적 검사, 합성 테스트, 실제 Silvaco 출력 검사를 섞지 않는다. 예약된 작업이 완료될 것으로 예상해 수치를 채우지 않는다.

## 결과와 재현성

1. 사용한 덱·사양과 실제 명령, Silvaco/DevEdit/ATLAS 버전, 실행 시각과 시간대, 종료 코드, 정상 종료/에러 로그를 남긴다.
2. 네이티브 바이어스와 export 범위 일치, 필수 점/NaN/누락/수렴, 단위, KCL을 확인한다. 일부 점만 있는 sweep은 전체 Id–Vg 완료라고 하지 않는다.
3. 실패·미완료도 로그와 원인을 남긴다. 아직 모르는 원인은 미확인으로 적는다. 성공 곡선만 골라 전체 성공으로 보고하지 않는다.
4. 분석 명령과 입력→그림 연결을 남긴다. 실측과 시뮬레이션을 구별한다. 모델에서 꺼진 물리는 관측되지 않았다고 검증된 것이 아니다.
5. 다른 원본의 해시를 바꾸지 않는다. 수정한 원본을 기존 결과인 것처럼 교체하지 않는다.

## GitHub에 올릴 파일과 별도 보관할 파일

| GitHub에 포함 | 별도 승인된 보관소에 원본 유지 |
| --- | --- |
| 덱, 사양, 사전계획, 분석 코드, 작은 원시 로그/export, 요약, 그림, 원본목록 | `.str`, `.zip`, 20 MiB 초과 파일, 대량 중간 결과 |

GitHub 웹은 25 MiB 제한이 있지만 이 팀의 제출 기준은 파일당 20 MiB 이하다. Git push의 서비스 제한과 별도로 적용한다. `.gitignore`는 이미 추적 중인 파일이나 웹 업로드를 소급해서 막지 않는다. 포함되지 않은 파일이 필요하면 요약만으로 재현 가능하다고 하지 말고 원본 접근 조건을 적는다.

PowerShell에서 원본 해시를 구하는 예:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath "D:\본인결과\device.str"
(Get-Item -LiteralPath "D:\본인결과\device.str").Length
```

보관소는 학교/팀이 승인한 서버·Drive 등의 **비밀값 없는 경로**를 사용한다. GitHub Releases/Drive 업로드를 자동 승인한 것은 아니다. 저작권이 있는 논문 전체 파일·상용 설치 파일·라이선스·개인정보·접속 정보는 공개 자료에 넣지 않는다.

## 검토와 main 반영

브랜치는 `exp/<아이디 또는 별칭>/<주제>-<날짜>-r01`, PR 제목은 `[실험] 이름 / 주제 / 실행ID`를 권장한다. 매번 공용 표 한 줄을 편집하지 않아도 본인 폴더를 찾아 결과를 볼 수 있게 한다. [팀원실험 색인](../../연구/팀원실험/README.md)은 고정된 팀원 입구만 제공한다.

검토자는 조건과 원시 근거, 단위, 실패 표시, 파일 용량/비밀정보, 기존 결과 보존을 확인한다. 코드 소유자는 저장소 소유자이며, main은 PR·승인 1명·소유자 검토를 요구하는 구성을 사용한다. 적용 여부는 [설정 기록](설정변경_20261125.md)을 확인한다. 소유자의 관리 작업은 관리자 예외를 이용할 수 있지만 팀원은 PR을 기본으로 한다. 승인 대기와 물리 검증 대기를 구분한다.

공용 기준 변경과 단순 결과 추가는 PR을 나눈다. 기존 실행 내용 정정은 새 실행 ID 또는 원본을 보존하는 정정 문서로 추가하고 변경 이유를 명시한다. 기술적으로 Git이 수정을 막는 것은 아니므로 diff 검토가 필요하다.
